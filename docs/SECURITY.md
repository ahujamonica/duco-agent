# Security and privacy posture

This is a local prototype. It handles health information, so the controls that are implemented and the controls that are **not** are listed here explicitly rather than implied by a padlock icon.

## Implemented

- **Authentication:** email + password; PBKDF2-HMAC-SHA256 with a per-user 16-byte salt and 240,000 iterations. Password never stored or logged.
- **Sessions:** signed JWT bearer tokens (HS256, server-side secret, 12-hour default expiry). Expired/invalid tokens are rejected; the client clears the session on 401.
- **Authorisation:** every family, policy, document, case, report and simulator request resolves the entity and verifies the signed-in user owns the family. A missing entity and another user's entity both return 404 (no existence oracle).
- **File storage:** uploads are stored under `data/uploads` with a random UUID name — never the user's filename and never inside the web root. Downloads go through `GET /api/documents/{id}/file`, which checks ownership and sets `Cache-Control: private, no-store`.
- **Upload validation:** extension allowlist, MIME allowlist, size cap (15 MB default), empty-file rejection, image verification through Pillow.
- **Duplicate detection:** SHA-256 per household; duplicates are reused rather than stored twice.
- **SQL injection:** all access through SQLAlchemy ORM/expression language; no string-concatenated SQL.
- **Response headers:** `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `Cache-Control: no-store` on API responses.
- **Secrets:** read from environment variables; no secret is committed. A development JWT secret is used only when `DUCO_JWT_SECRET` is unset, and the app should not be exposed with it.
- **Generated files:** reports are stored outside the web root and served only through the owner-checked download route.
- **Account deletion:** `DELETE /api/settings/account?confirm=true` deletes the user, cascades households/members/policies/documents/cases/results and removes uploaded files and reports.
- **Data export:** `GET /api/settings/export` returns a JSON copy of the user's households, policies and case results.
- **No third-party processing by default:** the deterministic pipeline (Tesseract, PyMuPDF, rule-based extraction, Decimal engine) runs locally. Optional LLM enrichment is off unless an API key is configured.

## Not implemented — do not treat this build as production-ready

- **Encryption at rest** for the SQLite database, uploads or generated reports. No KMS/key hierarchy, no envelope encryption.
- **Field-level encryption** for identifiers or clinical text.
- **Read audit logs.** Writes and agent actions are traced, but who opened which document is not logged.
- **Rate limiting, CAPTCHA, account lockout, breached-password checks.**
- **Consent and purpose limitation workflows.** There is no consent artefact per family member, no guardian consent for minors, no DPDP Act erasure/portability workflow beyond account deletion.
- **HTTPS/TLS termination and HSTS.** Run behind a reverse proxy with TLS and secure headers.
- **Backups, retention schedule and secure deletion of backups.**
- **Penetration test, formal threat model, dependency scanning, SBOM.**
- **Multi-tenant isolation at the database level.** Isolation is enforced in application code; a production build should add row-level security or per-tenant encryption.
- **Real insurer authentication and mTLS.** The `/mock-insurers/*` endpoints are unauthenticated sandbox endpoints by design. They must never be exposed to the internet in this form.
- **ABDM/ABHA integration, FHIR validation, HIE consent.** Not attempted.
- **Malware scanning of uploads.** File-type validation is not a substitute for an antivirus scan.

## Data handling in the demo

- All names, policies, amounts and documents in `fixtures/` are fictional and generated by `fixtures/generate_fixtures.py` or the demo seeder.
- The demo account is `demo@duco.health`. Its password is documented for evaluators; it is not a production credential.
- The demo seed can be reset from Settings, which removes the seeded household's uploads and database rows.
- The audio briefing is generated through gTTS, which sends the briefing text to Google's TTS service when network access is available. If that is unacceptable, set `DUCO_TTS=0`; the platform then writes only the script.
- If `DUCO_LLM_API_KEY` is configured, document text is sent to the configured OpenAI-compatible endpoint for optional enrichment. Leave it unset to keep all processing local.

## Recommendations before real patient data

1. Move to PostgreSQL with encryption at rest and per-tenant row-level security.
2. Put the API behind TLS, a WAF/rate limiter and a secrets manager; rotate the JWT secret.
3. Add KMS-backed envelope encryption for files and sensitive columns.
4. Add read/write audit logging with tamper-evident storage and retention rules.
5. Implement consent, guardian consent, purpose limitation and erasure workflows aligned with the DPDP Act and ABDM guidelines.
6. Add malware scanning and document sanitisation before OCR.
7. Authenticate and sign all real insurer/TPA integrations; remove or firewall any mock endpoint.
8. Commission a threat model and penetration test before launch.
